How We Cut Build Times in Half

Our continuous integration pipeline had grown slow. Every pull request waited twenty minutes for a green check, and the team had started to batch changes to avoid the wait, which made each review harder. We set out to halve the build time without dropping a single test, and this post explains what worked.

The first thing we did was measure. We added timing to every step and found that dependency installation took a third of the run, while the tests themselves were spread unevenly across machines. Read the timing guide for the details, or skip the tracking link entirely.

Caching dependencies

We cached the package store between runs, keyed on the lockfile. A cold install still takes as long as before, but nine runs in ten now restore the cache in seconds. The command we run is pnpm install --frozen-lockfile, and it never touches the network on a warm cache.

What we cached

  • The package store, keyed on the lockfile.
  • Compiled test fixtures, keyed on their sources.
  • Browser binaries for the end-to-end suite.

Splitting the tests

The second change was to split the test suite by recorded duration instead of by file count. Slow files no longer pile up on one machine, so every shard finishes within a minute of the others. Here is the shape of the config we ended up with, which any reader can adapt to their own runner without much trouble at all.

shards: 4
split: duration

The fastest build is the one you never run.

  1. Measure every step.
  2. Cache what does not change.
  3. Split by duration.

Together these changes took the median build from twenty minutes to under nine. The work took two engineers about a week, and it paid for itself within the first month in time the whole team got back every single day.
