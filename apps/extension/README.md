# linkables for Chrome (beta)

A Manifest V3 extension: click the toolbar button and the pop-up saves the tab
you're on, then lets you pin it or file it in a collection. Signed in on
linkables.app, the extension signs itself in (`src/connect`); otherwise the
pop-up offers Sign in with linkables.app, Continue with Google, or the 6-digit
email code. The side panel (`sidepanel.html`, opened from the pop-up's All
links tile or Alt+Shift+L) shows the current page with Save, your recent and
pinned links, and your collections with sharing. This is the Phase 1 beta,
installed by hand with **Load unpacked**; Alt+Shift+S and multi-tab saves are
Phase 2 (`docs/PLANNING.md`).

The panel has no `tabs` permission, so it sees a tab's address only where
`activeTab` allows: after the toolbar button or the side panel shortcut is used
on that tab. On any other tab it says so instead of offering Save.

## Build

The build reads the same variables as the web build, from the shell or
`apps/extension/.env` (gitignored):

| Variable | Production value |
|---|---|
| `VITE_APP_URL` | `https://linkables.app` (the web app; the API is under `/api/v1` there) |
| `VITE_SUPABASE_URL` | the Supabase project URL |
| `VITE_SUPABASE_ANON_KEY` | the public anon key |

```sh
pnpm --filter extension build     # dist/, ready for Load unpacked
pnpm --filter extension release   # release/linkables-chrome-<version>.zip from dist/
pnpm --filter extension watch     # rebuilds dist/ on change while you work
pnpm --filter extension release:store  # release/linkables-chrome-store-<version>.zip for the Web Store
pnpm --filter extension store:images   # redraws the store icon, promo tile and screenshots in store/
```

`release:store` builds into `dist-store/` without the manifest `key` (the Web
Store refuses one and assigns its own id) and stops unless `VITE_APP_URL` is
`https://linkables.app` and `VITE_SUPABASE_URL` is https. Publishing it is
in [STORE.md](STORE.md).

`manifest.json` is generated by the build (`manifest.ts`): permissions are only
`activeTab`, `storage`, `identity` (the Google sign-in window) and `sidePanel`,
host permissions only `VITE_APP_URL` and `VITE_SUPABASE_URL`, and the one content
script runs only on `VITE_APP_URL`. The build writes the pop-up, the side panel,
the service worker (`worker.js`) and the content script (`content-script.js`,
built on its own as one classic script). The version comes from `package.json`; bump it for each
release.

## Load unpacked

1. `chrome://extensions`, turn on **Developer mode** (top right).
2. **Load unpacked**, pick `apps/extension/dist` (or the unzipped release folder).
3. Pin the linkables icon from the puzzle-piece menu.

After a rebuild, press the reload arrow on the extension's card.

## Extension id and key

The id is fixed by the public key in `manifest.ts` (`MANIFEST_KEY`):

```
ekgbmopoceccloaibfknnbnohkpbkili
```

so every install, unpacked or packed, has the origin
`chrome-extension://ekgbmopoceccloaibfknnbnohkpbkili`. The API must list that
origin in `CORS_ORIGINS` (see `deploy/.env.production.example`).

The private key is **not** in the repo. Load unpacked needs only the public
key; the private key matters only to pack a `.crx` or to upload to the Chrome
Web Store with the same id. The owner keeps it outside the repo. Losing it means
a new key pair, a new id and a new `CORS_ORIGINS` entry.

## Distribution

On every push to `main`, CI builds the extension against production, zips it,
and the web image serves the zip at
`https://linkables.app/downloads/linkables-chrome.zip` for anyone who installed
it by hand. Everyone else installs it from the Chrome Web Store, which
`https://linkables.app/extension` links to. The same run builds the
Web Store zip and keeps it as the `linkables-chrome-store` run artifact, which
is not served publicly.

## Tests

```sh
pnpm --filter extension test   # unit tests (Vitest)
pnpm --filter extension e2e    # loads the unpacked build in Chromium against the e2e API
```

The e2e suite builds the extension into `e2e/dist` for an app origin on port
3271 (`E2E_EXTENSION_APP_PORT`), where it serves the web app and passes `/api`
to a local API on port 3270 (`E2E_EXTENSION_API_PORT`). It answers the
Supabase calls itself, and needs `TEST_DATABASE_URL` like the web e2e suite.

## Sign-in from linkables.app

The extension never copies the website's session: Supabase rotates refresh
tokens and treats reuse as theft, which would sign both out. Instead, on the
app's pages the content script and the web app hand over a one-time token:

1. The signed-in web app posts `linkables:extension-ping` to its own window.
2. If the extension is signed out (and the user didn't sign out of it by hand),
   the worker makes a nonce and the content script posts `extension-hello`.
3. The web app calls `POST /api/v1/extension-sessions` and posts
   `extension-session { nonce, tokenHash }`.
4. The worker checks the nonce (single use, two minutes) and verifies the token
   into the extension's own session, then the page gets `extension-connected`.

Every message is `window.postMessage` to the app origin, checked for source,
origin and shape (`packages/shared/src/extension-sessions`). The pop-up's
button opens `/extension/connect`, which also resumes after a sign-out and
whose tab the worker closes once signed in. The Google button runs Supabase's
PKCE flow through `chrome.identity` in the worker; Supabase's Redirect URLs
must list `https://<extension id>.chromiumapp.org/**` for each id.
